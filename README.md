# ReBench

> AI benchmarks shouldn't be trusted. They should be reproduced.

ReBench is an open, community-run database of AI inference benchmarks.
Every number on this site is backed by a complete, machine-readable record:
model, revision, quantization, hardware, engine, software versions, benchmark
version, prompt and generation configuration, and the measured result.

There are no editorial picks. There are no averages of unknown origin. There
are runs — each one reproducible, each one traceable to a commit.

## How it works

```
LOCAL MACHINE      contributor runs the standardized runner on their own rig
     │
BENCHMARK RUNNER   fixed workload, fixed config, pinned versions
     │
RAW RESULT         one JSON file per run, validated against schema/
     │
GITHUB             submitted as a pull request into results/{family}/
     │
VALIDATION         schema check + cross-field coherence checks in CI
     │
WEBSITE            regenerated from data/benchmarks.json
```

GitHub is the source of truth. The website is a projection of the repository.

## Repository layout

```
ReBench/                       # this Next.js application (app router, repo root)
├── app/                       # routes and pages
├── components/                # shared UI
├── lib/                       # data access and formatting helpers
├── scripts/                   # data generation + schema validation
├── data/
│   └── benchmarks.json        # index generated from results/ (website input)
├── schema/
│   └── benchmark.schema.json  # JSON Schema for a single run record
├── benchmark/                 # standardized runner + pinned workloads
└── results/                   # one directory per model family (awaiting first measured run)
    ├── qwen/
    ├── llama/
    └── deepseek/
```

`data/benchmarks.json` is regenerated by CI whenever a result file lands in
`results/`. Contributors never edit it by hand.

## Current state

The synthetic dataset has been removed. The website starts with an empty,
honest index and is populated only from measured JSON records committed under
`results/`. CI regenerates the index on every result change; no page invents
benchmark numbers.

## Development

```sh
npm install
npm run dev        # http://localhost:3000
npm run build      # production build (static export to out/, deployed to GitHub Pages)
npm run lint
npm run typecheck
npm run generate:data  # regenerate data/benchmarks.json
```

## Docker runner

The website's **Methodology → Evaluation suites → Run a benchmark** section
contains the same copyable flow. ReBench currently accepts an
OpenAI-compatible `/v1/chat/completions` endpoint and writes one redacted JSON
record; the browser cannot directly inspect a Docker process running on a
contributor's machine.

```sh
mkdir -p out
docker build -t rebench-runner:dev -f benchmark/Dockerfile benchmark
docker run --rm --user "$(id -u):$(id -g)" --network host \
  -v "$PWD/out:/output" \
  -e REBENCH_HARDWARE="your GPU" -e REBENCH_GPU_VENDOR="NVIDIA" \
  -e REBENCH_VRAM_GB=16 -e REBENCH_RAM_GB=32 -e REBENCH_CPU="your CPU" \
  --env REBENCH_API_KEY rebench-runner:dev \
  --base-url http://127.0.0.1:8000/v1 --model your-model \
  --suite performance --manifest benchmark/performance.json \
  --family your-family --contributor Nilabh-code \
  --model-revision 0000000 --git-commit 0000000 \
  --output /output/run.json --status-file /output/status.json
```

The pinned manifest fixes prompt, sampling, warmups, repetitions, and streaming.
The runner writes `run.json` plus a live `status.json` with phases
`fingerprinting`, `warming_up`, `measuring`, `complete`, or `failed`.
Each result includes raw per-trial TTFT/generation metrics. Prompt TPS uses
provider timing metadata when the API returns `usage.prompt_ms`; otherwise the
record explicitly says `timingSource: estimated_from_ttft`.

Copy the output into `results/<family>/`, run `npm run validate` and
`npm run generate:data`, then submit a pull request. CI validates the record;
after merge, GitHub Pages rebuilds the measured leaderboard. `test-writing`,
`refactoring`, `codebase-qna`, and `bug-fixing` are versioned suite identifiers
in `benchmark/suites.json`; their task fixtures and evaluators must be
published before claiming scores.
